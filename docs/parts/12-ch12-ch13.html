12.4 Conseils de publication

  • Image : joignez une capture du site ou l’image og-image.png. Un post avec visuel attire davantage l’attention.
  • Lien : LinkedIn réduit parfois la portée des posts contenant un lien. Vous pouvez publier le texte avec l’image, puis mettre le lien dans le premier commentaire. Dans ce cas, écrivez « Lien en commentaire » dans le post.
  • Moment : un mardi, mercredi ou jeudi matin (heure de Madagascar) est un créneau classique pour les posts professionnels.
  • Mention : ne taguez pas des recruteurs ou des entreprises sans leur accord.
  • Vérité : ne rajoutez pas de chiffres ou de clients que le portfolio ne peut pas prouver.
  • Réponses : prévoyez de répondre aux commentaires le jour même ; c’est ce qui transforme une publication en conversation.
  • Réutilisation : le même texte peut servir de description sur GitHub, dans un CV ou dans un e-mail de candidature, en l’adaptant.
Après publication

Ajoutez le lien du portfolio dans votre profil LinkedIn (section « Coordonnées » ou « Site web »), dans votre signature e-mail et sur votre CV. Un portfolio sert surtout quand il est facile à retrouver.

Chapitre 13Annexes

13.1 Les dix erreurs à éviter

  1. Modifier seulement le français. Le test de parité échouera, ou l’anglais affichera l’ancien texte.
  2. Chercher les projets en base. Ils sont dans content.ts.
  3. Inventer une valeur de visual. Le type n’accepte que trois valeurs ; ajoutez le rendu ou utilisez une galerie.
  4. Mettre une image externe sans remotePatterns. next/image la refusera.
  5. Utiliser un nom de fichier avec des espaces ou des majuscules. Vercel est sensible à la casse.
  6. Oublier de redéployer après un changement de variable. Les variables ne sont pas toujours rechargées par un simple push.
  7. Mettre l’URL avec un slash final. siteUrl le retire, mais autant écrire l’URL propre.
  8. Utiliser la base de production pour les previews. Les tests polluent les vrais messages et les vraies visites.
  9. Committer .env.local. Vérifiez git status avant chaque premier push.
  10. Croire qu’un test vert suffit. Le formulaire, l’admin et l’assistant doivent être testés à la main après déploiement.

13.6 Fin du guide

Ce document décrit l’état du projet à sa date de rédaction. Si une procédure ou un fichier change, mettez à jour le guide en même temps que le code : c’est ce qui évite de se retrouver, six mois plus tard, devant une documentation qui ne correspond plus à la réalité.
