Chapitre 09Qualité, tests et sécurité

Avant chaque déploiement, quatre commandes suffisent à éviter la majorité des régressions : tests, lint, vérification TypeScript et build. Ce chapitre explique ce que chacune vérifie et ce qu’elle ne vérifie pas.

9.1 Les commandes

CommandeCe qu’elle fait
npm testLance Vitest une fois. Vérifie la parité FR/EN, l’authentification et les regex de validation.
npm run test:watchRelance les tests à chaque modification.
npm run lintESLint avec les règles Next.js et TypeScript.
npx tsc --noEmitVérifie les types sans générer de fichiers. (Le build le fait aussi.)
npm run buildCompile le site, vérifie les types, génère les routes et les pages statiques.
npm run startDémarre le build de production en local (après npm run build).

9.2 Les tests présents

FichierCe qu’il vérifie
src/lib/content.test.tsLa structure de fr et en est identique (mêmes clés, mêmes longueurs de tableaux) et aucun texte n’est vide. C’est le test le plus important pour éviter les oublis de traduction.
src/lib/auth.test.tsLe mot de passe correct est accepté ; les mauvais formats sont refusés ; la détection de mot de passe faible fonctionne.
src/lib/validation.test.tsLes regex e-mail et téléphone définies dans le test. Il n’importe pas de module validation.ts : c’est un test de référence, pas la validation utilisée en production.
src/components/language-provider.test.tsxLe provider de langue et la bascule FR/EN.
Ce que les tests ne couvrent pas

Il n’y a pas de test end-to-end du formulaire, de l’admin ou de l’assistant. Ces parcours doivent être vérifiés manuellement après déploiement (voir 11.9). Les tests ne remplacent pas un clic réel sur le site.

9.3 Ce que vérifie le build

  • Les imports et les alias @/.
  • Les types de content.ts : un champ manquant dans un projet, une certification ou un témoignage fait échouer la compilation.
  • Les composants client/serveur : un hook utilisé dans un composant serveur provoque une erreur.
  • Les routes : pages, API, sitemap, robots, manifest.
  • Les images locales référencées.

9.4 Vérifications manuelles avant mise en ligne

  • La page d’accueil se charge en français et en anglais.
  • Le thème clair/sombre fonctionne et persiste après rechargement.
  • Le menu mobile s’ouvre, se ferme avec Échap et verrouille le scroll.
  • Les liens d’ancrage du header et du footer arrivent sur les bonnes sections.
  • Les projets vedettes affichent leurs images et leurs liens.
  • Le carrousel répond aux flèches et se met en pause au survol.
  • Le formulaire envoie un message et affiche l’écran de succès.
  • Le message apparaît dans /admin, puis peut être supprimé.
  • Une visite apparaît dans l’onglet Audience (hors /admin).
  • L’assistant répond à une question simple.
  • Les PDF de certification s’ouvrent.
  • Le CV se télécharge.
  • Les pages /projets, /contact, /competences redirigent correctement.
  • /sitemap.xml et /robots.txt sont accessibles.

9.5 Accessibilité et préférences

  • Un lien « Aller au contenu » est présent au début du document.
  • Les animations respectent prefers-reduced-motion : compteurs, machine à écrire, galerie et révélations.
  • Le menu mobile gère Échap et le focus.
  • Les images ont des textes alternatifs ; les icônes décoratives sont masquées aux lecteurs d’écran.
  • Les contrastes du thème sombre sont définis dans globals.css.
  • Les formulaires ont des libellés associés et des messages d’erreur explicites.

9.6 Sécurité : la checklist

  • .env.local n’est jamais commité.
  • ADMIN_PASSWORD fait au moins 12 caractères et n’est pas un mot courant.
  • Le jeton Turso est stocké uniquement dans Vercel et .env.local.
  • La clé Groq/Gemini n’est jamais exposée côté client (pas de préfixe NEXT_PUBLIC_).
  • Les dépendances sont à jour : npm audit --omit=dev.
  • Les en-têtes de sécurité sont actifs en production.
  • L’admin est en noindex et n’est pas lié depuis le site.
  • Les messages reçus ne sont pas exportés dans un dépôt public.
  • Le CV et les attestations ne contiennent pas d’informations que vous ne voulez pas publier.
Ne jamais faire

Ne mettez jamais ADMIN_PASSWORD, TURSO_DB_TOKEN, GROQ_API_KEY ou GOOGLE_AI_API_KEY dans un fichier versionné, une capture d’écran, un ticket ou ce PDF. Si un secret a fuité, révoquez-le et recréez-le immédiatement.

Chapitre 10Développement local

10.1 Prérequis

  • Node.js 20 ou 22 (le projet utilise Next.js 16).
  • npm (fourni avec Node).
  • Git.
  • Un éditeur (VS Code, Cursor…).

10.2 Installation

cd /chemin/vers/le/portfolio
npm install

Utilisez npm ci si vous voulez reproduire exactement les versions du package-lock.json (CI, machine neuve).

10.3 Fichier d’environnement local

Copiez le modèle et remplissez les valeurs : 

cp .env.example .env.local
# Site
NEXT_PUBLIC_SITE_URL=http://localhost:3000

# Admin
ADMIN_PASSWORD=un-mot-de-passe-fort-de-12-caracteres-minimum

# Base (laisser vide pour SQLite local)
TURSO_DB_URL=
TURSO_DB_TOKEN=

# Assistant IA
AI_PROVIDER=groq
GROQ_API_KEY=
GOOGLE_AI_API_KEY=
Valeurs factices

Les valeurs ci-dessus sont des exemples. Ne recopiez pas un vrai mot de passe ou une vraie clé dans un document, un chat ou un commit.

10.4 Initialiser la base locale

npm run db:init

Sans TURSO_DB_URL, cela crée data/portfolio.db. Le dossier data/ est ignoré par Git.

10.5 Lancer le serveur

npm run dev

Ouvrez http://localhost:3000. Pour tester sur un autre port : 

npm run dev -- --port 3100

10.6 Tester le build de production en local

npm run build
npm run start

Le build de production est plus strict que le mode développement : c’est celui qui doit passer avant un déploiement.

10.7 Docker (optionnel)

Le dépôt contient un Dockerfile et un script run.sh pour un déploiement auto-hébergé. Ce n’est pas la voie utilisée par Vercel. 

docker build -t zomahefaranaivo/portfolio .
./run.sh latest

Le script monte ./data dans /app/data et charge .env.local. Sans variables Turso, la base SQLite persiste dans ce volume.

10.8 Problèmes locaux fréquents

SymptômeSolution
Port 3000 déjà utilisénpm run dev -- --port 3100 ou arrêtez l’autre processus.
Variables non prises en compteRedémarrez npm run dev : les variables serveur ne sont pas toujours rechargées à chaud.
Base introuvableLancez npm run db:init. Vérifiez que data/ est accessible en écriture.
Erreur de moduleSupprimez node_modules et .next, puis npm ci.
Tests qui échouent après une modification de contenuVous avez probablement oublié une clé en français ou en anglais. Lisez le chemin indiqué par content.test.ts.
Image 404Vérifiez le nom exact dans public/ et la casse.
Assistant 503Ajoutez une clé IA dans .env.local et redémarrez.
