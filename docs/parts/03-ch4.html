Le serveur rend le HTML avec le contenu français par défaut. Au chargement, LanguageProvider lit zm_locale dans localStorage : si le visiteur avait choisi l’anglais, React remplace les textes sans rechargement. Le HTML initial reste en français, ce qui est cohérent avec lang="fr" et le référencement.

4.2 Le changement de langue

  1. Le visiteur clique sur LanguageToggle.
  2. toggleLocale() bascule fr ↔ en dans le contexte.
  3. useMemo recalcule c = getContent(locale).
  4. Tous les composants abonnés à useI18n() se re-rendent avec les nouveaux textes.
  5. Un effet met à jour document.documentElement.lang et écrit zm_locale.
Conséquence pour le SEO

Le site n’a pas deux URLs (/fr et /en) ni de balises hreflang. Le contenu anglais est une bascule cliente. Les moteurs indexent donc principalement la version française. C’est un choix assumé : une seule page, un seul canonical, pas de contenu dupliqué. Si vous voulez un vrai SEO bilingue plus tard, il faudra créer des routes /en et des métadonnées dédiées — ce n’est pas le fonctionnement actuel.

4.3 Le thème clair/sombre

  1. Un script inline dans layout.tsx lit theme dans localStorage avant le rendu et ajoute la classe light ou dark sur <html>.
  2. ThemeProvider (next-themes) prend le relais : thème clair par défaut, pas de suivi du système.
  3. ThemeToggle change la classe et persiste le choix.
  4. globals.css définit les variables de couleurs pour :root et .dark.

  • Le champ website est un honeypot : s’il est rempli, le formulaire simule un succès sans envoyer.
  • Le consentement est obligatoire côté client.
  • Le type de besoin est choisi dans contact.types et préfixé au message.

4.5 Le suivi d’audience

  1. VisitTracker s’exécute à chaque changement de pathname.
  2. Il ignore /admin.
  3. Il fabrique ou récupère un identifiant visiteur dans localStorage (zm_visitor_id).
  4. Il envoie { path, referrer, visitorId } à /api/visits avec keepalive.
  5. La route ignore les robots, déduit l’appareil et le pays, puis insère dans page_views.
  6. /admin appelle GET /api/visits pour obtenir les agrégats.
Vie privée

Aucun cookie publicitaire n’est posé. L’identifiant visiteur est un UUID stocké localement, utilisé uniquement pour compter les visiteurs uniques. Les robots sont filtrés et l’admin n’est pas mesuré. Si vous ajoutez un bandeau de consentement, faites-le avant le tracking.

Le cookie est HttpOnly, SameSite=Strict, et Secure en production. Il contient une date d’expiration et une signature HMAC-SHA256 calculée avec ADMIN_PASSWORD comme secret. Changer le mot de passe invalide donc toutes les sessions en cours. Le serveur accepte aussi, pour compatibilité, l’ancien en-tête Authorization: Bearer <mot_de_passe>.

L’écran admin ne stocke pas de jeton dans localStorage : il s’appuie uniquement sur le cookie. Au premier chargement, il appelle /api/admin/session. Si la réponse est 401, l’écran de connexion reste affiché. Si une requête ultérieure renvoie 401, la session est considérée expirée.

4.8 Le SEO et le partage social

  1. siteUrl est calculé depuis NEXT_PUBLIC_SITE_URL (sans slash final) ou vaut le domaine par défaut.
  2. layout.tsx utilise cette URL pour metadataBase, le canonical, l’Open Graph, Twitter et le JSON-LD.
  3. sitemap.ts et robots.ts utilisent la même valeur.
  4. public/og-image.png (1200×630) est l’image de partage.
  5. Les pages /projets, /contact, /competences sont en noindex et redirigent vers les ancres.
Si vous changez de domaine

Modifiez NEXT_PUBLIC_SITE_URL dans Vercel, puis redéployez. Les métadonnées sont générées au build : sans redéploiement, le canonical, le sitemap et le JSON-LD continueront de pointer vers l’ancien domaine.
