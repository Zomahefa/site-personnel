Chapitre 07Admin, base de données et sécurité

Le portfolio n’a pas de CMS. La base de données sert uniquement à recevoir les messages du formulaire et à compter les visites. L’administration est une page privée qui lit ces deux tables. Ce chapitre explique le schéma, les règles d’accès et les opérations courantes.

Trois index sont créés :

idx_messages_created_at      ON messages(created_at)
idx_page_views_created_at    ON page_views(created_at)
idx_page_views_visitor       ON page_views(visitor_id)

7.2 Turso ou SQLite local ?

src/lib/db.ts choisit automatiquement : 

const isTurso = !!process.env.TURSO_DB_URL;

// Si TURSO_DB_URL est défini :
createClient({ url: TURSO_DB_URL, authToken: TURSO_DB_TOKEN })

// Sinon :
createClient({ url: "file:data/portfolio.db" })
  • En local, sans variables Turso : un fichier data/portfolio.db est créé. Il est ignoré par Git.
  • En production, avec TURSO_DB_URL et TURSO_DB_TOKEN : la base distante est utilisée.
  • Les tables sont créées automatiquement au premier accès grâce à ensureSchema(), mais il est recommandé de lancer npm run db:init pour vérifier les droits et initialiser explicitement.
Ne pas mélanger les environnements

Si vous lancez npm run dev avec les variables Turso de production dans .env.local, vous écrirez dans la vraie base pendant vos tests. Utilisez soit le SQLite local, soit une base Turso dédiée au développement.

7.3 Initialiser la base

npm run db:init

Le script scripts/init-db.mjs :

  1. Charge .env.local via @next/env.
  2. Choisit Turso si TURSO_DB_URL existe, sinon data/portfolio.db.
  3. Exécute les CREATE TABLE IF NOT EXISTS et les index.
  4. Affiche la cible, le nombre de messages, le nombre de vues et les tables.
✓ Base initialisée
  cible        : Turso
  messages     : 0
  pages vues   : 0
  tables       : messages, page_views

Le script est idempotent : vous pouvez le relancer sans perdre les données.

7.4 L’administration

URL : /admin. La page est en noindex, nofollow et n’est pas listée dans le sitemap. Elle n’est pas liée depuis le site public.

Connexion

  1. Le formulaire envoie le mot de passe à /api/admin/login.
  2. La route limite à 6 tentatives par 15 minutes et par IP.
  3. Si ADMIN_PASSWORD n’est pas configuré : réponse 503 explicite.
  4. La comparaison se fait en temps constant (XOR caractère par caractère).
  5. En cas de succès, un cookie zm_admin_session est posé : HttpOnly, SameSite=Strict, Secure en production, durée 8 heures.
  6. Le jeton est expiration.signature, signature HMAC-SHA256 avec ADMIN_PASSWORD.

Onglet Messages

  • Liste les messages du plus récent au plus ancien.
  • Recherche locale sur le nom, l’e-mail et le message.
  • Affiche les coordonnées, le type de besoin et la date formatée en heure de Fianarantsoa.
  • Suppression unitaire avec confirmation.

7.5 Authentification et sécurité

Le mot de passe admin

  • Variable ADMIN_PASSWORD, jamais dans Git.
  • Minimum recommandé : 12 caractères, majuscules, minuscules, chiffres et symboles.
  • isWeakPassword() avertit dans les logs si le mot de passe est faible, mais ne bloque pas le démarrage.
  • Changer le mot de passe invalide toutes les sessions existantes (la signature change).

Les limites de débit

RouteLimiteFenêtre
/api/admin/login6 tentatives15 minutes / IP
/api/messages (POST)5 messages10 minutes / IP
/api/visits (POST)60 vues10 minutes / IP
/api/assistant (POST)25 questions10 minutes / IP
Limite en mémoire

Ces compteurs vivent dans une Map en mémoire, par instance serverless. Ils ne sont pas partagés entre toutes les instances Vercel et se réinitialisent à froid. C’est une protection simple contre les abus basiques, pas un pare-feu. Pour une protection forte, utilisez un service de rate limiting distribué (Upstash, Redis, Vercel Firewall…).

7.6 Opérations courantes

Supprimer les messages de test

Le plus simple : connectez-vous à /admin et supprimez-les un par un. Pour repartir de zéro sur la base locale : 

rm -f data/portfolio.db
npm run db:init
Ne faites pas cela en production

Ne supprimez jamais data/portfolio.db sur un serveur en production : cela effacerait les messages et les visites. Sur Turso, une suppression est explicite et doit être réfléchie.

Nettoyer les visites de test sur Turso

turso db shell portfolio-zomahefa "DELETE FROM page_views;"

À utiliser uniquement juste après la mise en ligne, pour repartir d’un compteur propre. Les messages se suppriment depuis l’admin.

Sauvegarder la base

turso db shell portfolio-zomahefa ".dump" > backup-portfolio.sql

Conservez ce fichier hors du dépôt Git. Pour restaurer, utilisez turso db shell avec le fichier SQL, ou recréez une base et rejouez les insertions.

Vérifier le contenu d’une table

turso db shell portfolio-zomahefa "SELECT COUNT(*) FROM messages;"
turso db shell portfolio-zomahefa "SELECT COUNT(*) FROM page_views;"
turso db shell portfolio-zomahefa "SELECT name FROM sqlite_master WHERE type='table';"

7.7 Vie privée et données

  • Les messages contiennent des données personnelles (nom, e-mail, téléphone). Ne les exportez pas dans un dépôt public.
  • L’admin n’est pas indexé, mais il est accessible à toute personne qui connaît l’URL et le mot de passe.
  • Les visites ne stockent pas l’IP en base : elle sert uniquement au rate limiting en mémoire.
  • Le pays et l’appareil sont des données agrégées, pas des identifiants individuels.
  • Prévoyez une politique de conservation : supprimez les messages traités après un délai raisonnable.
